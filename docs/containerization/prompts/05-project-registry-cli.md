# Agent: Project Registry and CLI Commands

You are working on the `master` branch of Drem Orchestrator, a Go-based multi-agent task orchestrator. Your task is Phase 1 foundation work for the containerization initiative: build the host-side multi-project registry (`~/.drem/projects.toml`) and wire up the `drem project` subcommands that maintain it. This is what lets the developer register `drem-orchestrator` and `drem-canvas` as two concurrent projects, and it is the data source Kyle will query to discover project orchestrators.

## Deliverables

### New files

#### 1. `internal/projects/registry.go`

Pure TOML load/save over `~/.drem/projects.toml`.

- `type Project struct { Name string; BareRepoPath string; Language string; OrchURL string; ContainerImageOverrides map[string]string }` — the override map maps agent type (`"coder"`, `"merger"`, `"csuite-mike"`, etc.) to a specific image tag; empty for the default
- `type Registry struct { Path string; Projects []Project }`
- `func DefaultPath() string` — returns `$HOME/.drem/projects.toml`
- `func Load(path string) (*Registry, error)` — reads the file; returns an empty `Registry` with `Projects: nil` if the file does not exist (no error)
- `func (r *Registry) Save() error` — writes atomically via tempfile + rename
- `func (r *Registry) Add(p Project) error` — returns an error if `p.Name` already exists
- `func (r *Registry) Remove(name string) error` — returns an error if not found
- `func (r *Registry) Get(name string) (*Project, bool)`

Allowed languages: `"go"`, `"cpp"`. Validate on add.

Required fields on add: `Name`, `BareRepoPath`, `Language`, `OrchURL`. Validate `BareRepoPath` exists and is a bare repo (check for `HEAD` and `objects/` under the path).

#### 2. `internal/projects/template.go`

Renders the per-project compose file from an embedded template.

- `//go:embed templates/project-compose.yml.tmpl` drives a `text/template`
- `type TemplateData struct { ProjectName string; OrchURL string; Language string; WorkerImage string; MergerImage string; CsuiteImages map[string]string; BareRepoPath string; SharedToken string }` — `SharedToken` is the per-project token for `POST /internal/logs` (generate a fresh UUID on registration)
- `func Render(data TemplateData) ([]byte, error)`
- `func WriteProjectCompose(projectName string, data TemplateData) (string, error)` — writes to `$HOME/.drem/projects/<name>/compose.yml`, returns the resolved path

`WorkerImage`, `MergerImage`, and the `CsuiteImages` map are populated by callers from `projects.toml` overrides plus language-driven defaults (`drem-worker-go:latest` vs `drem-worker-cpp:latest`).

#### 3. `internal/projects/templates/project-compose.yml.tmpl`

Compose-file template. Prompt 16 is responsible for the full set of service definitions; here, produce a skeleton with TODO comments where prompt 16 will fill in the detail:

```yaml

  # TODO(prompt-16): merger-pool (2-3 replicas)
```

Keep the skeleton minimal and correct TOML/YAML syntax; do not guess at fields that prompt 16 will define.

#### 4. `cmd/drem/project.go`

Cobra-style (or flag-based — match whatever `cmd/drem/main.go` already uses) subcommand dispatch for `drem project ...`.

- `drem project register --name <n> --bare <path> --language <go|cpp> --orch-url <url>` — validates, calls `registry.Add`, then `template.WriteProjectCompose`, prints the generated compose path
- `drem project list` — prints a table: name, language, bare path, orch URL
- `drem project remove <name>` — removes from registry and deletes `~/.drem/projects/<name>/compose.yml` (warn if the compose is still referenced by running containers but proceed anyway; this is a host-side record, not a live invariant)
- `drem project show <name>` — prints the full `Project` record plus the path to its compose file

## Scope Limitation

- This prompt does not own the compose template's real service definitions. Prompt 16 fills in the TODO blocks once the images and orchestration integrations land.
- The `register` command does not `docker compose up` the generated file. Starting the stack is a separate operational step.
- The registry is host-side state only. It is not replicated into any project's SQLite database, and no running orchestrator reads it — only Kyle (prompt 14) and the `drem project` CLI do.
- No locking on `projects.toml` beyond atomic write. Multi-writer contention is out of scope (solo developer host).
